# 10 · 发布后故障变多了吗？基线比较与统计口径

**中心思想**：工程判断要建立在可复现的数据上；“错误数更多”不必然代表错误率升高，但两种指标都应呈现。

**本关真实成果**：一个可用于开发者发布检查的日志对比命令。

## 1. 运行一份可解释的对比

```sh
cargo run -p loglens -- compare loglens-playground/baseline.log loglens-playground/candidate.log
```

初始演示数据：

| 指标 | 旧版本 | 新版本 |
|---|---:|---:|
| 已识别日志记录 | 8 | 8 |
| ERROR + FATAL | 1 | 3 |
| 记录级错误率 | 12.50% | 37.50% |
| 未识别行 | 0 | 1 |

因此可报告“错误率**增加 25.00 个百分点**”，但**不能据此推断服务请求失败率增加了 25%**：日志事件不等价于请求，两个文件样本也不一定覆盖相同业务量。

## 2. 读源码

看 `Summary::count`、`errors` 和 `error_rate`；了解 Rust 中 `u64` 与 `f64` 的区别，为什么整数计数在输出百分比时需要转换，为什么零有效记录必须单独处理。

尝试创建一份只含无效文本的日志，与正常日志比较，观察结果：CLI 会说明其中一份没有有效记录，因此不可判断性能或故障率改善。

## 3. 本关 RED → GREEN 任务

发布流水线需要一个**可选**检查：`compare --fail-on-regression`。要求当新文件和旧文件都存在有效记录，且新文件的记录级错误率严格高于旧文件时，以非零退出码结束，并在 stderr 给出“错误率上升”。

```sh
cargo test -p loglens --test challenges mission_10_fail_on_regression -- --ignored --exact
```

这不是通用故障检测阈值；它是一个由使用者显式开启的严格比较规则。不得将其默认启用，也不得假设不同样本、日志策略或业务负载下的比率可以直接比较。数据缺失、无效行较多时应明确给出“无法判断”的处理策略，而非默认为通过。

完成后回归：`cargo test --workspace`。
