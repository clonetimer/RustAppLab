# 第 27 关 · 不看答案也能继续：观察、预测、修改、验证

**中心思想**：工具提供的是下一步方向和明确的失败反馈，学员仍要自己动手操作，并说明为什么代码应该这样写。

## 一、让 LabQuest 指出下一项真实工作

在项目根目录创建新案例：

```sh
cargo run -p labquest -- start coached-case
cargo run -p labquest -- next coached-case
```

`next` 根据当前案例真实文件和验收结果给出：**本步骤目标、当前失败原因、涉及的 Rust 知识、建议命令、第一层提示以及下一次检查命令**。它不修改文件、不编译任何学生代码；不用将提示当作已完成的操作。

按推荐命令生成第一份 FileQuest 报告，再执行：

```sh
cargo run -p labquest -- next coached-case
```

这次应推进到事故日志取证。继续完成模拟、报告和代码修改，你会发现它基于实际产物判断，而不是记录你点过哪些按钮。

## 二、错误与提示如何使用

程序告诉你“哪个条件尚未满足”，你应该先检查文件与测试输出。如果还不明白，只用第一层提示；第二层提示给更具体的技术方向；第三层才出现参考表达式。

```sh
cargo run -p labquest -- hint 5 1
cargo run -p labquest -- hint 5 2
cargo run -p labquest -- hint 5 3
```

例如在 Rust 代码关卡，如果 `test-app` 报 `timeout_ms=400` 场景失败，请检查是否把条件写成 `>=`。若 `timeout_ms=150` 场景失败，检查是否把摘要写死为零。这类错误来自**程序的实际行为**，不是工具随意给出的主观评语。

## 三、一次真正的学习循环

1. **先观察**：打开你自己的 `project/src/main.rs`，找到 `for` 循环与 `timeout`。
2. **先预测**：运行 `practice`，用 `predict <阈值> <预测数>` 自查边界规则。
3. **亲手实现**：改动 Rust 源码，不使用静态 `errors=0`。
4. **实际验证**：运行 `test-app`，根据编译器或不同阈值失败信息修复代码。
5. **交付作品**：用 FileQuest 更新地图，用 SafeSync 保存项目快照，再由 `finish` 导出调查报告。

请在完成后回答三个问题，而不是只截一张 6/6 的图片：为什么源码变更后需要重跑证明？为什么一次样例通过不能证明通用性？为什么项目快照应当包含源码和配置，而不是只保存日志？

## 四、没有被自动证明的事情

通过此关**不代表新手已经掌握所有 Rust 语言能力**，也不等同于有人类学员参与的学习效果实验。我们已经验证了工具逻辑、实测编译和程序输出，但实际的新手上手耗时、误解率和代码迁移能力仍需收集真实使用反馈才能评价。
